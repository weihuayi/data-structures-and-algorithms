# Deck 课件修订方法

本指南适用于本仓库课程 Deck 的审阅与修订，依据 D008、D009 的具体修订经验形成。它补充[课程整体设计方案](course-design-plan.md)，不替代课程认知框架，也不把两份课件的实现方式推广为所有课件的固定模板。这里的经验有源文件和交互实现依据，尚不能据此断言课堂学习效果已得到验证。

当前共同约定与约束强度见 [课程课件共性约定](deck-contract.md)。本指南解释方法与反例，公共组件与检查命令以 [工具说明](../../tools/deck/README.md) 为准。优先复用已验证模式；偏离默认时说明教学原因和影响，不能豁免正确性或必要输入。局部修订不自动触发整讲迁移。

## 从学习任务确定修订范围

先写清学生在这一页需要做什么：识别结构、比较表示、预测一步、解释条件、运行程序，还是独立解决新问题。再检查完成任务所需的信息是否在场。

审阅记录宜包含“页标题／问题、可观察缺陷、影响的任务、最小修订、验证方式”。页码用于定位，标题用于抵抗增删页造成的偏移。区分内容错误、表达风险和可选改进，不用美化意见充当缺陷。

修订时同时检查关联链。例如位置编号改从 0 开始，不能只改图中数字，还要核对父子位置公式、边界、表格、代码与说明；改了遍历顺序，应核对状态序列、输出、例题答案与完成标记。先明确影响范围，再修改，避免无关重排。

## 让关系可见，让表示可对应

| 触发情境 | 修订动作 | 安全反例或适用边界 | 无关情境 |
| --- | --- | --- | --- |
| 学生必须识别父子、左右子树或局部范围 | 在当前任务处提供可直接辨认的结构图，保留稳定标识 | 一个简单关系已由文字完整表达时，不必补图 | 课程安排、阅读提示无需树图 |
| 从情境转成数学结构，再转成存储或程序 | 并列对应对象、符号、字段或位置，说明转换条件 | 表达式树可用字符作结点标签，不必把每个字符都放入公式环境 | 纯导航信息不需要三栏映射 |
| 比较不同遍历或不同表示 | 尽量沿用同一例子，减少无关变化 | 检验迁移能力时应换结构、取值或情境 | 封面不需要延续例树 |
| 图中既有结构关系又有执行方向 | 区分父子边与执行路径，明确颜色或标记语义 | 有向图中的方向属于对象本身，应保留箭头 | 不要求所有图取消箭头 |

D008 的树、二叉树、位置与链式表示为这些动作提供案例；D009 在同一棵树上比较遍历，随后用恢复问题检验是否理解了分割依据。复用例子服务于比较，不能替代新的独立练习。

引用教材定义时保持定义完整，并与案例解释分开。图示可以帮助理解，但不能偷偷替换定义的前提。例如有序性、空树、结点标识是否互异等条件，应在实际影响结论的位置出现。

## 把解题输入、提示和答案分开

独立预测之前，学生必须看得到题目、已知条件、操作规则和必要图示；提示、结果、解释可以折叠。不要把解题必需的输入一起隐藏，也不要让标题、图注或教师注记摘要提前泄露答案。

D008 的展品案例可以按课堂需要展开示例树；D009 的恢复练习把提示与答案分开，并以同名折叠组控制一次只展开一种内容。这是具体教学选择，不意味着所有图都默认隐藏。

教师注记承载可公开的展开脚本、追问与边界说明。默认收起，打印不展开正文。教师私有备注仍不进入公开仓库。折叠能调整呈现时机，不能替代删减内容和合理的课堂时间预算。

## 分步演示必须表达算法状态

只在学生需要追踪状态变化时使用分步演示。静态结构识别用图即可；一句说明足以回答的问题不必动画化。

每种演示先确定状态语义，再实现界面：

- 当前操作是什么，哪一部分是输入，哪一部分是工作状态，哪一部分是输出？
- “进入结点”“访问结点”“离开调用”“整棵子树完成”是否被明确区分？
- 栈、队列、递归帧的排列方向和当前位置是否有说明？
- 输出是否只在算法规定的访问时刻增加，完成标记是否满足相应条件？
- 上一步、下一步、重置是否保留可解释且一致的状态？

D009 的状态由共享 `tree_trace.py` 生成，页面展示确定的快照。逻辑测试核对输出、容器变化与恢复分割；浏览器检查切换、隐藏和布局。两层检查分别回答算法状态与界面行为问题，互不替代。通用组件进入共享层，具体例树和课堂问题留在 Deck 中。

恢复二叉树等逆向任务要交代成立条件。给出一种构造不等于证明唯一；程序能运行也不等于输入满足条件。必要时加入反例，检验学生是否知道方法的适用边界。

## 公式、代码与图示各司其职

数学表达式使用本地 KaTeX 支持的 LaTeX 数学环境：行内 `\(...\)`，独立公式 `\[...\]`。多行推导可使用 `aligned`。启用与转义方法见[工具说明](../../tools/deck/README.md)。

代码保留代码语法，SVG 中的结点名称保持可读标签；不要为了满足“统一公式”把程序、普通标识或导航菜单包装成数学表达式。说明中的真正数学关系仍用数学环境。公式渲染成功只验证语法与呈现，公式正确性、索引起点和适用条件另行核对。

## 验证完整的课堂操作路径

构建后先确认 `index.html` 与源同步，再检查默认投影状态、每个受支持的步骤、返回与重置、折叠展开以及打印和连续阅读的基本行为。至少检查 1280×720 和 1440×900 两种投影尺寸。不要只看第一页或最终状态截图。

教师注记展开后可纵向滚动；学生必须即时读取的主内容和展开答案仍应检查投影溢出。多个折叠区是否允许同时展开、展开后是否替换预览图，应由教学意图决定并单独核验。自动检查不能判断字号是否适合教室最后一排，仍需人工看图与实际课堂反馈。

| 验证层 | 可形成的证据 | 不能据此宣称 |
| --- | --- | --- |
| 源与生成物一致性 | 当前页面确实来自当前源 | 页面或算法正确 |
| 状态逻辑测试、C 编译运行 | 所测输入和断言成立 | 覆盖全部输入或全部数学结论 |
| 浏览器检查 | 指定尺寸、已覆盖操作路径未发现所检查缺陷 | 所有交互、浏览器、投影设备都可用 |
| 人工审阅与课堂反馈 | 具体可读性、理解困难与时间分配证据 | 未观察到的学习效果已改善 |

运行入口、依赖、退出码和未覆盖项处理见[验证工具说明](../../tools/deck/README.md#课件验证)。未支持的交互、嵌套折叠与超出自动覆盖范围的组合展开需要人工补查；记录具体页和操作，不得把“未覆盖”写成“通过”。

## 修订完成前的逐页问题

1. 当前问题明确吗？完成任务所需的输入、条件和图示是否在场？
2. 对象、表示、操作和输出是否区分清楚？跨页名称与编号是否一致？
3. 学生能先独立预测吗？折叠前后是否分别形成完整、可读的状态？
4. 关键结论是否给出依据与适用条件？有没有需要保留的反例？
5. 交互的中间状态、末态和重置是否正确？失败或未覆盖项是否记录？
6. 修改是否影响课堂时间、断点或可砍页？设计卡是否同步？
7. 源、生成页面和演示代码是否一致？验证结论是否只覆盖实际执行的检查？
